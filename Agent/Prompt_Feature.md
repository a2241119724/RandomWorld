请基于 ./Agent 中的 Agent 体系，自动完成一次“发现游戏业务功能缺口 -> 选择最适合的候选 -> 生成任务卡 -> 实现新功能 -> 验证记录 -> 更新候选完成状态”的完整流程。

重要要求：
- 不要向我提问。
- 不要等待我确认。
- 如果遇到需要人工确认的高风险候选，请自动跳过它，选择下一个低风险或中风险候选。
- 一次只实现一个游戏业务相关的新功能。
- 本次目标不是单纯生成开发工具，而是自动发现并开发可服务于游戏玩法、成长、资源、关卡、战斗、UI 行为或玩家体验链路的新功能。
- 优先选择低风险、高价值、边界清晰、可通过代码或已有入口接入的游戏业务功能。
- 优先选择以下类型的游戏业务功能：
  - 成就 / 任务 / 目标进度追踪
  - 关卡结算奖励计算
  - 角色属性、Buff、技能冷却、消耗校验等轻量玩法逻辑
  - 道具获得、使用、掉落模拟或规则校验
  - 玩家行为统计、战斗事件记录、关卡表现评分
  - 已有 UI 入口但缺少行为逻辑的功能
  - 已有数据结构但缺少业务处理流程的功能
  - 已有脚本雏形、TODO、空方法但未完成的功能
  - 不直接破坏资源的只读型业务校验或业务模拟功能
- 不要优先选择纯开发效率工具，例如只读扫描器、Editor 报告工具、模板生成器等，除非当前项目中没有安全的游戏业务候选。
- 不要优先选择会直接修改 Scene、Prefab、ScriptableObject、StreamingAssets、存档结构、Photon 同步或 AssetBundle 的功能。
- 如果所有游戏业务候选都属于高风险，则只实现一个不改业务资产的只读业务分析 / 业务模拟 / 业务报告功能。
- 生成候选功能列表时，必须为每个候选分配唯一编号和完成状态，便于后续判断该候选是否已经处理完成。
- 完成功能实现与验证后，必须回写 feature_discovery.md 中对应候选的状态标记。

候选状态规则：
- `[TODO]`：待处理，尚未实现。
- `[DONE]`：已完成，已实现并完成可行验证。
- `[SKIPPED]`：已跳过，通常因为高风险、边界不清晰、需要人工确认或涉及敏感资源修改。
- `[BLOCKED]`：受阻，已分析但因缺少环境、依赖、权限或无法验证而未完成。
- `[PARTIAL]`：部分完成，已实现部分能力，但仍存在明确未完成项。

候选功能列表格式必须包含：

| 状态 | 候选ID | 功能名称 | 业务类型 | 来源信号 | 玩家价值 | 项目价值 | 风险 | 成本 | 优先级 | 推荐 Agent | 推荐 Skill | 处理说明 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|

| [TODO] | G002 | 玩家任务进度追踪功能 | 任务系统 | 代码中存在 Quest/TODO/Progress 相关空方法 | 高 | 高 | 中 | 中 | P0 | QuestAgent | ProgressTrackSkill | 可通过代码接入，需避免修改存档结构 |
| [SKIPPED] | G003 | 自动修复 Prefab 中缺失的按钮绑定 | UI 行为 | UI Prefab 存在 Missing Reference | 中 | 中 | 高 | 高 | P1 | UIFixAgent | PrefabModifySkill | 涉及 Prefab 直接修改，跳过 |
| [DONE] | G004 | 道具使用冷却校验功能 | 道具系统 | ItemUse 逻辑存在重复冷却判断 | 中 | 高 | 低 | 低 | P1 | ItemAgent | CooldownLogicSkill | 已完成并生成验证记录 |

执行步骤：

1. 读取并理解以下文件：
   - Agent/README.md
   - Agent/Docs/ImplementationRoadmap.md
   - Agent/Docs/SkillCatalog.md
   - Agent/Config/agent_registry.json
   - Agent/Config/task_router.json
   - Agent/Templates/agent_task_card.md

2. 只读扫描项目上下文，重点检查：
   - README、Agent 文档、历史任务卡中的后续建议
   - Scripts/2D 中与游戏业务相关的 TODO、FIXME、空方法、临时实现、重复模式
   - 角色、道具、技能、任务、关卡、战斗、奖励、背包、UI、存档、网络同步等相关代码
   - Resources/SO、Resources/Tilemap、Resources/Images 中是否存在“有数据但无业务逻辑”的功能缺口
   - 已有系统中“有数据但无 UI / 有 UI 但无行为 / 有行为但无验证 / 有配置但无消费逻辑 / 有枚举但无处理分支”的半完成链路
   - 存档、Photon、AssetBundle、资源引用等高风险区域的只读业务检查机会
   - 历史 feature_discovery.md 和 task_*.md 中已经标记为 `[DONE]` 的候选，避免重复实现同一功能

3. 生成目录：
   - Agent/Reports/<今天日期>/

4. 输出游戏业务功能发现报告：
   - Agent/Reports/<今天日期>/feature_discovery.md

   报告必须包含：
   - 扫描范围
   - 候选功能列表
   - 每个候选的唯一候选ID
   - 每个候选的状态标记：`[TODO]`、`[DONE]`、`[SKIPPED]`、`[BLOCKED]` 或 `[PARTIAL]`
   - 每个候选的业务类型，例如：关卡、战斗、道具、任务、成就、UI 行为、资源规则、玩家成长、数据统计等
   - 每个候选的来源信号、玩家价值、项目价值、风险、成本、优先级、推荐 Agent、推荐 Skill
   - 推荐优先开发的 1-3 个游戏业务功能
   - 被跳过的高风险候选及原因
   - 已完成候选的任务卡路径、修改文件和验证记录摘要

5. 自动选择一个最适合立即开发的游戏业务候选功能：
   - 只能从 `[TODO]` 状态的候选中选择
   - 不得重复选择历史记录中已经 `[DONE]` 的候选
   - 优先选择 P0
   - 其次选择 P1
   - 必须满足：低风险或中风险、边界清晰、可在一个任务卡内完成、不会直接破坏业务数据或 Unity 资源引用
   - 必须能明确说明该功能属于哪条游戏业务链路，例如：
     - 玩家触发条件
     - 输入数据
     - 核心逻辑
     - 输出结果
     - 对玩家体验或系统完整性的价值
   - 如果候选涉及 Scene、Prefab、ScriptableObject、StreamingAssets、存档、Photon 或 AssetBundle 的直接修改，则跳过，并将状态更新为 `[SKIPPED]`
   - 如果候选需要新增存档字段、改网络协议、改资源序列化结构或强依赖美术资源，则跳过或降级为只读业务分析功能

6. 为选中的候选生成任务卡：
   - Agent/Reports/<今天日期>/task_<候选ID>_<功能名>.md

   任务卡必须包含：
   - 候选ID
   - 原始候选
   - 当前状态
   - 游戏业务类型
   - 玩家触发场景
   - 输入数据
   - 输出结果
   - 任务分类
   - 负责 Agent
   - 需要的 Skill
   - 影响路径
   - 不应触碰路径
   - 风险等级
   - 执行步骤
   - 验证步骤
   - 回滚方案
   - 结果区

7. 按任务卡实现该游戏业务功能：
   - 只修改和该任务直接相关的文件
   - 优先放在 Scripts/2D、Scripts/2D/Gameplay、Scripts/2D/System、Scripts/2D/UI 或项目已有相近业务目录
   - 如果项目已有对应模块，优先沿用已有模块结构，不另起一套重复系统
   - 保持现有项目命名、目录结构和代码风格
   - 不做无关重构
   - 不修改用户已有的无关改动
   - 不直接修改 Scene、Prefab、ScriptableObject、StreamingAssets、存档结构、Photon 同步或 AssetBundle
   - Unity 资源相关修改必须保留 .meta；如果无法安全处理，则不要修改该资源
   - 如果功能需要 UI 但不能安全修改 Prefab 或 Scene，则实现业务逻辑层，并提供可供现有 UI 调用的公开接口
   - 如果功能需要数据但不能安全修改 ScriptableObject，则使用默认配置、代码内安全默认值或只读适配方式，并在任务卡中记录后续接入建议

8. 完成后运行可行的验证：
   - 至少做静态检查、语法检查或编译相关检查
   - 如果不能运行 Unity 编译或 Play Mode，要在任务卡中明确写出未验证原因
   - 如果新增游戏业务逻辑，要验证：
     - 输入为空时是否安全
     - 边界值是否安全
     - 重复调用是否稳定
     - 不依赖未创建资源时是否能正常工作
     - 不修改高风险业务资产
   - 如果新增 Editor 菜单、业务模拟器或报告工具，要验证脚本路径、输出路径和基本扫描逻辑

9. 更新任务卡结果区，写入：
   - 最终状态：`[DONE]`、`[PARTIAL]` 或 `[BLOCKED]`
   - 已完成内容
   - 修改的文件
   - 验证结果
   - 未完成项
   - 剩余风险
   - 后续建议

   - 将该候选状态从 `[TODO]` 更新为：
     - `[DONE]`：功能已实现且完成可行验证
     - `[PARTIAL]`：功能部分完成
     - `[BLOCKED]`：因环境、依赖或权限问题未能完成
   - 在该候选的“处理说明”中补充：
     - 对应任务卡路径
     - 修改文件
     - 验证结果摘要
     - 是否仍有剩余风险
   - 对自动跳过的候选，将状态更新为 `[SKIPPED]`，并写明跳过原因

   - 业务类型
   - 最终状态
   - 修改了哪些文件
   - 验证结果
   - 剩余风险
